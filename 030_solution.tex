\section{Особенности реализации}

В настоящем разделе будут описаны ключевые особенности реализации статического анализатора.

\subsection{Архитектура}

Статический анализатор разделён на два модуля.
Первый модуль отвечает за анализ декларативной спецификации в LLVM, второй ответственен за анализ модели на Sail.

\begin{itemize}
  \item Модуль, ответственный за анализ LLVM, получает на вход скомпилированные в единый \texttt{JSON} \texttt{.td} файлы, содержащие описание спецификации RISC-V ISA.
        Затем из входного \texttt{JSON} файла для каждой инструкции извлекаются следующие свойства:
        \begin{itemize}
          \item мнемоника (извлекается по ключу \texttt{AsmString});
          \item входные операнды (по ключу \texttt{InOperandList});
          \item выходные операнды (по ключу \texttt{OutOperandList});
          \item неявные входные операнды (по ключу \texttt{Uses});
          \item неявные выходные операнды (по ключу \texttt{Defs});
          \item может ли инструкция читать память (по ключу \texttt{mayLoad});
          \item может ли инструкция писать в память (по ключу \texttt{mayStore});
          \item для какой разрядности (\texttt{RV32} или \texttt{RV64}, или для обеих) определена инструкция (по ключу \texttt{Predicates}).
        \end{itemize}
        Наконец, анализатор генерирует модуль, который содержит всю собранную информацию о свойствах каждой инструкции и предоставляет интерфейс для доступа к информации.
        Генерация отдельного модуля со всей информацией реализована для того, чтобы при каждом запуске анализатора не анализировать один и тот же \texttt{JSON}, тем самым экономя драгоценное время.

  \item Второй модуль, отвечающий за статический анализ модели на Sail, получает на вход \texttt{.sail} файлы, которые содержат определение модели.
        Далее при помощи библиотеки компилятора языка Sail производится синтаксический анализ и вывод типов, на выходе получая типизированное AST.
        Затем на полученном ранее типизированном AST запускаются анализы, о которых подробнее далее.
\end{itemize}

\subsection{Специализация}

Как было сказано ранее, эмулятор sail-riscv представляет из себя интерпретатор некоторого AST, каждый узел которого параметризован некоторыми параметрами.
Один узел AST модели может представлять сразу несколько инструкций, но специализация узла представляет из себя конкретную инструкцию.

Например, узел AST из листинга \ref{itype} специализированный по последнему параметру
\begin{lstlisting}[caption={}, language={}]
  ITYPE (imm, rs1, rd, RISCV_ADDI)
\end{lstlisting}
представляет инструкцию
\begin{lstlisting}[caption={}, language={}]
  addi rd, rs1, imm
\end{lstlisting}

\subsubsection{Сопоставление узлов AST и мнемоник}

Во-первых, необходимо было определить за какие инструкции отвечает каждый узел AST модели sail-riscv.
Для этого производился анализ специализаций функций \texttt{assembly}, которые как раз отвечают за отображение узлов AST в мнемоники инструкций.

\subsubsection{Специализация \texttt{execute} функций}

Узел \texttt{ITYPE}, определенный на листинге \ref{itype}, параметризован четырьмя параметрами: непосредственным значением ширины 12 бит, двумя индексами регистров и целочисленной операцией, которая представлена типом перечисления (enum). В зависимости от значения последнего параметра по-разному вычисляется результат в \texttt{execute} функции, задающей семантику исполнения узла \texttt{ITYPE}, на листинге \ref{execute_itype}.
При этом в общем случае в зависимости от параметров, семантика исполнения может кардинально изменятся, например, при одном значении параметра может происходить чтение какого-то регистра, а при другом не происходить; при одном значении может читаться память, а при другом происходить запись в память. Поэтому важно специализировать.

% Для того чтобы статический анализатор исследовал семантику исполнения специализированного узла AST, который представляет конкретную инструкцию, необходимо специализировать тело \texttt{execute} функции, а также тела всех функций, которые вызывает данная \texttt{execute} функция.

Анализатор специализирует \texttt{execute} функции только по параметрам типов перечисления (enum) и логических типов (bool).

Например, для специализации \texttt{ITYPE (imm, rs1, rd, RISCV\_ADDI)} (специализирован только последний параметр) тело, соответствующей \texttt{execute} функции, определённой на листинге \ref{execute_itype}, после специализации выглядело следующим образом.

\begin{lstlisting}[caption={Пример специализированной по параметру \texttt{execute} функции из листинга \ref{execute_itype}}, language=sail, frame=single]
function clause execute (ITYPE (imm, rs1, rd, RISCV_ADDI)) = {
  let rs1_val = X(rs1);               // read the rs1
  let immext : xlenbits = EXTS(imm);  // sign-extend imm
  let result : xlenbits = rs1_val + immext;
  X(rd) = result;                     // write result to rd
  RETIRE_SUCCESS                      // successful termination
}
\end{lstlisting}

Однако после описанной выше специализации в теле функции могут остаться выражения, результат которых нигде не используется.
При этом такие выражения могут негативно влиять на анализ. Например.

\begin{lstlisting}[caption={Пример функции, после наивной специализации которой могут остаться неиспользуемые выражения, негативно влияющие на дальнейший анализ}, language=sail, numbers=left, numberstyle=\color{gray}, escapechar=!, label=remove_exprs_example]
function clause execute (PEXT_32_16_MUL_ADD(rs2, rs1, rd, op)) = {
 let rs1_val = X(rs1); let rs2_val = X(rs2); let !\colorbox{yellow!20}{rd\_val}! = X(rd);
 result : xlenbits = zeros();
 foreach (i from 0 to (sizeof(xlen) - 32) by 32) {
    let rs1_word = slice(rs1_val, i, 32);
    let rs2_word = slice(rs2_val, i, 32);
    let !\colorbox{yellow!20}{rd\_word}! = slice(!\colorbox{yellow!20}{rd\_val}!, i, 32);
    result[(i+31)..i] = match op {
      SMMWB  => smmw(rs1_word, slice(rs2_word, 0, 16)),
      KMMAWB => kmmaw(rs1_word, slice(rs2_word, 0, 16), !\colorbox{yellow!20}{rd\_word}!),
      ...
    };
 };
 X(rd) = result;
 RETIRE_SUCCESS
}
\end{lstlisting}

\begin{lstlisting}[caption={Вспомогательные выражения}, language=sail, numbers=left, numberstyle=\color{gray}, escapechar=!, label=helper-exprs]
let rd_val = X(rd);
result[(i+31)..i] = smmw(rs1_word, slice(rs2_word, 0, 16));
\end{lstlisting}

Тело функции из листинга \ref{remove_exprs_example} сокращено для краткости. Будем считать, что после 10 строчки ни один идентификатор, определённый ранее, не используется.

В функции листинга \ref{remove_exprs_example} параметр \texttt{op} имеет тип перечисления со значениями \texttt{SMMWB}, \texttt{KMMAWB} ...
Если специализировать тело этой функции по параметру \texttt{op} со значением \texttt{SMMWB}, то выражение на 8 строчке сократится до выражения, представленного на строчке 2 листинга \ref{helper-exprs}.
Но после такой специализации связка (binding) \texttt{rd\_word}, определенная на строке 7, нигде больше не используется.
Поэтому её определение можно удалить из специализированной версии функции.
При этом после такого удаления становится не используемой связка \texttt{rd\_val}, поэтому выражение (в котором происходит чтение регистра!) определения этой связки (строчка 1 листинга \ref{helper-exprs}) можно удалить из 2 строчки листинга \ref{remove_exprs_example}.

Таким образом, если не производить подобный проход, то для инструкции \texttt{SMMWB} и многих других было бы найдено ненужное чтение из регистра \texttt{rd}.

\subsection{Поиск входных и выходных операндов}
\label{sec:ins_outs_analyze}

В модели sail-riscv для взаимодействия с регистрами используются следующие функции:
\begin{itemize}
  \item \texttt{X} для чтения или записи регистров общего назначения (General-Purpose Registers);
  \item \texttt{F} для чтения или записи вещественных регистров;
  \item \texttt{V} для чтения или записи векторных регистров.
\end{itemize}

Причем если вызов одной из выше определенных функций происходит справа от присваивания, то выбирается перегрузка для чтения регистра, если слева, то для записи.

Рассмотрим следующую функцию.

\begin{lstlisting}[caption={Пример определения функции, задающей семантику исполнения инструкции \texttt{add}}, language=sail, escapechar=!, label=rtype_speced, frame=single]
function clause execute ( ADD(rs2, rs1, rd) ) = {
    let rs1_val = !\colorbox{green!20}{X(rs1)}!;
    let rs2_val = !\colorbox{green!20}{X(rs2)}!;
    let result : xlenbits = rs1_val + rs2_val;
    !\colorbox{yellow!20}{X(rd)}! = result
    RETIRE_SUCCESS
}
\end{lstlisting}

Функция на листинге \ref{rtype_speced} определяет семантику исполнения для инструкции \texttt{add}.
Семантика следующая. Во-первых, при помощи функции \texttt{X} считываются значение входных регистров \texttt{rs1} и \texttt{rs2}.
Затем вычисляется результат, и результат записывается в регистр \texttt{rd}, используя перегрузку функции \texttt{X} для записи.

Для поиска входных и выходных регистров строился граф вызовов функций \cite{ryder1979call_graph}.
Затем производился обход графа вызовов и анализ того, какие функции, с какими аргументами вызывали функции для взаимодействия с регистрами.

Таким образом, для инструкции \texttt{add} регистры \texttt{rs1} и \texttt{rs2} являются входными, а регистр \texttt{rd} выходным.

\subsection{Анализ обращения инструкции к памяти}

Для работы с памятью в sail-riscv используются функции \texttt{read\_ram} и \texttt{write\_ram}.
Для того чтобы определить читает или пишет инструкция память, для каждой специализации функции \texttt{execute} проверялась достижимость вершин \texttt{read\_ram} и \texttt{write\_ram} в ранее определённом графе вызовов функций.

Однако любая инструкция, которая работает с адресами, при трансляции виртуального адреса в физический может как писать, так и читать память.
Это происходит из-за взаимодействия с таблицей страниц (page table).
\begin{itemize}
  \item Чтение из памяти может потребоваться, когда при трансляции виртуального адреса в физический в TLB (Translation Lookaside Buffer — специализированный кэш для ускорения трансляции адресов, хранящий информацию о недавних трансляциях) отсутствует необходимая запись. В этом случае требуется обход таблицы страниц, которая хранится в памяти.
  \item Запись в память может потребоваться, когда при трансляции виртуального адреса в физический необходимо обновить бит доступа (A --- accessed) или модификации (D --- dirty) у записи таблицы страниц.
\end{itemize}

Обращения к памяти при трансляции виртуальных адресов в физические игнорировались.
Для этого при решении задачи достижимости вершин \texttt{read\_ream} и \texttt{write\_ram} в графе вызовов игнорировался вызов функции \texttt{translateAddr}, которая ответственна за трансляцию виртуального адреса в физический.

\subsection{Особенности расширения \texttt{P}}

RISC-V --- это модульная ISA, которую можно расширять при помощи расширений.
Расширение \texttt{P} (packed SIMD) --- это расширение, предназначенное для ускорения целочисленных вычислений и вычислений с фиксированной точкой.

Проект sail-riscv-p\footnote{\url{https://github.com/umcann123/sail-riscv-p} (дата обращения: \DTMdate{2025-02-17}).} --- это форк sail-riscv с реализованным расширением \texttt{P}.
В этом расширении существуют инструкции, у которых один операнд может представлять сразу пару регистров.

\begin{lstlisting}[caption={Пример \texttt{execute} функции, задающей семантику исполнения инструкциям, которые работают с парами регистров}, language=sail, label=depxlen, frame=single]
function clause execute(PEXT_64BITS_ADD_SUB(rs2, rs1, rd, op)) =
{
  results : bits(64) = zeros();
  rs1_val : bits(64) = zeros();
  rs2_val : bits(64) = zeros();
  if sizeof(xlen) == 32
  then {
    rs1_val = X(rs1 | 0b00001) @ X(rs1 & 0b11110);
    rs2_val = X(rs2 | 0b00001) @ X(rs2 & 0b11110);
  }
  else { ... };
  results = match op {
    ADD64   => rs1_val + rs2_val,
    ...
  };
  if sizeof(xlen) == 32
  then {
    X(rd | 0b00001) = results[63..32];
    X(rd & 0b11110) = results[31..0];
  }
  else { ... };
  RETIRE_SUCCESS
}
\end{lstlisting}

% Функция на листинге \ref{depxlen} в случае RV32 (то есть выполняется условие \texttt{sizeof(xlen) == 32}) работает с парами регистров.

Нам интересно определять тип операндов (представляют ли они пару или нет), потому что он потенциально может быть неправильно определен в спецификации в LLVM.

\begin{lstlisting}[caption={Пример выражения, в котором происходит чтение и конкатенация значений из парных регистров}, language=sail, label=read_op]
X(rs1 | 0b00001) @ X(rs1 & 0b11110)
\end{lstlisting}

Для анализа типа операнда использовался эвристический алгоритм. Рассмотрим алгоритм на примере выражения из листинга \ref{read_op}.

\begin{enumerate}
  \item Представление программы в ANF \cite{flanagan1993essence} (A-Normal Form --- форма представления программы, при которой все аргументы функций тривиальны, т.~е. константы или переменные).
        \begin{lstlisting}[caption={ANF выражения из листинга \ref{read_op}}, language=sail, label=anf]
let a1 = rs1 | 0b00001 in
let a2 = rs1 & 0b11110 in
X(a1) @ X(a2)
        \end{lstlisting}
  \item Определение входных и выходных регистров по алгоритму описанному в \ref{sec:ins_outs_analyze}. Для выражения из листинга \ref{anf} регистры \texttt{a1} и \texttt{a2} являются входными.
  \item Построение и анализ data flow графа \cite{allen1976program}

\subsubsection{Анализ чтений и записей контрольно-статусных регистров}

В Sail для определения регистра существует ключевое слово \texttt{register}.
Все регистры представляют из себя глобальные переменные некоторого типа, с которыми можно работать как с обычной переменной.

\begin{lstlisting}[caption={Пример определения регистра в sail-riscv}, language=sail]
register marchid : xlenbits
\end{lstlisting}

Для расширения \texttt{P} необходимо было дополнительно определить для каждой инструкции какие CSRs (Control/Status Registers) она может читать и писать.

Для того чтобы определить обращается ли какая-то специализация \texttt{execute} функции (другими словами инструкция) к контрольно-статусным регистрам, производился рекурсивный обход всех вызываемых ею функций.
В процессе обхода отслеживались присваивания переменным. Если переменная представляла контрольно-статусный регистр, значит происходила запись в регистр, и такое обращение запоминалось.
Аналогично, отслеживались использования переменных.
Если используемая переменная --- контрольно-статусный регистр, значит происходило чтение этого регистра, и такое обращение запоминалось.

\section{Найденные расхождения}


Расхождения в LLVM 19 и sail-riscv\footnote{\url{https://github.com/riscv/sail-riscv/commits/05b845c91d1c1db7b361fc8d06e815b54ca0b07a} (дата обращения: \DTMdate{2025-05-17}).}.

\begin{enumerate}
  \item Регистр \texttt{SP} (stack pointer) не является явным аргументом в sail-riscv для инструкций:
        \texttt{c.addi16sp}, \texttt{c.addi4spn}, \texttt{c.fldsp}, \texttt{c.flwsp}, \texttt{c.fsdsp}, \texttt{c.fswsp}, \texttt{c.ldsp}, \texttt{c.lwsp}, \texttt{c.sdsp}, \texttt{c.swsp}.

        Инструкции имеют разный синтаксис.

        %         \begin{multicols}{2}

        %           \begin{lstlisting}[title={\centering\texttt{в LLVM}}, linewidth=5.4cm]

  \item Для расширения векторных инструкций было найдено два типа расхождений:

          \item для 28 инструкций в LLVM не указывается, что регистр \texttt{vd} является входным;
          \item для 255 инструкций в LLVM не указывается, что регистры \texttt{v0} и \texttt{vd} являются входными.

\end{enumerate}

Расхождения в расширении \texttt{P} в LLVM и sail-riscv-p\footnote{\url{https://github.com/umcann123/sail-riscv-p} (дата обращения: \DTMdate{2025-04-17}).}.
\begin{enumerate}
  \item В sail-riscv-p не хватает инструкции \texttt{rev}, в LLVM --- \texttt{pktt32}, \texttt{clo32}, \texttt{clo8}, \texttt{clo16}, \texttt{pkbb32}.


  \item В LLVM указано для 22 инструкций, что они читают контрольно-статусный регистр \texttt{vxsat} (используется как флаг переполнения).
        В sail-riscv-p 124 инструкции только пишут в регистр \texttt{vxsat}.
        Других обращений к контрольно-статусным регистрам не найдено.

\end{enumerate}
